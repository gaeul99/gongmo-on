공내비 대시보드 챗봇 계획서

대시보드를 “보는” 화면에서 “묻는” 화면으로. 대시보드가 집계한 현황을 근거로 마감·응모·관심을 답하고, 공모전 추천과 아이디어 브레인스토밍까지 맡기는 대화형 도우미.

01

목표와 성공 기준

대시보드는 흩어진 현황을 한 화면에 모았고, 챗봇은 그 화면을 질문할 수 있게 만든다. “이번 주에 뭐 마감해?”라고 물으면 대시보드가 계산해 둔 D-x를 그대로 답한다. AI가 날짜와 건수를 새로 계산하지 않는다 — 이것이 이 챗봇의 설계 축이다. 챗봇 마스코트 이름은 공내비에서 따온 “나비”로 제안한다(기존 레버리·콩콩이와 같은 계열).

성공 기준

  • 근거 있는 답변 — 사실(마감일·건수·목록)은 전부 대시보드 집계 스냅숏에서 온다. 스냅숏에 없으면 “모른다”고 답한다. 기존 분석 AI의 “전달되지 않은 사실을 만들어 내지 않는다” 원칙과 동일.
  • 키 입력 후 바로 대화 — 시작 화면에 채워 넣을 것은 API 키 하나다. 입력 즉시 인사말과 예시 질문이 준비된다.
  • 상태가 글자보다 먼저 읽힌다 — 키 등록 여부·전송 중·오류를 배지와 타이핑 인디케이터로 표시한다.
  • 오류마다 복구 길이 있다 — 키 오류는 재입력 화면으로(대화는 유지), 서버 오류는 재시도 버튼으로 이어진다.
  • 새로 배울 것이 없다 — 기존 집계 모듈·OpenAI SDK 호출 패턴·보라 액센트 카드 스타일을 전부 재사용한다.
02

모델·연결 정보

결과 화면의 아이디어 분석과 같은 OpenAI 호환 게이트웨이를 쓴다. 다른 점은 두 가지다 — 모델이 gpt-5-luna로 고정되고, API 키를 .env가 아니라 챗봇 시작 화면에서 입력받는다.

03

챗봇 역할 정의

범위는 두 갈래다 — 대시보드의 숫자를 묻고 답하는 일, 그 숫자를 바탕으로 추천하고 브레인스토밍하는 일. 둘 다 같은 스냅숏을 근거로 한다.

역할질문 예시근거 데이터

하지 않는 일

  • 앱 밖 공모전 검색 — 챗봇이 아는 공모전은 앱 데이터(접수 중 4개 · 기준일 명시)뿐이다. 밖을 물으면 검색 팝업의 “국내 공모전 전체 검색”을 안내한다.
  • 대화 기록 영속화 — 탭을 닫으면 키와 대화가 함께 사라진다. 다시 열면 새 대화다.
  • 키 없는 대화 · 모델 변경 — 키가 없으면 전송 자체가 막히고, 모델은 gpt-5-luna로 고정이다.

왜 백엔드를 거치는가

  • CORS 회피 — mlapi.run이 브라우저에서의 직접 호출을 허용한다는 보장이 없다. 백엔드(3000)를 거치는 서버 간 호출이면 제약이 없다.
  • 기존 패턴 재사용 — ai.service.ts가 이미 OpenAI SDK + baseURL 주입 + 오류 매핑을 하고 있다. 챗 서비스는 키를 .env가 아니라 요청 헤더에서 받는 변형이다.
  • 통제 지점 — 키 비기록 규칙, 60초 타임아웃, 모델명 고정을 서버 한 곳에서 관리한다.

05

API 키 처리와 보안

“챗봇 시작 시 입력”이 이 기능의 요구사항 축이다. 키는 어디에도 저장되지 않고, 이 탭의 sessionStorage에만 살아 있다.

  1. 시작 화면패널을 처음 열면 키 입력 화면 — 비밀번호형 입력 필드와 “대화 시작” 버튼만 있다
  2. 보관입력한 키를 sessionStorage 키 gongnabi:chat-key에 저장 — 탭을 닫으면 브라우저가 지우고, 탭이 살아 있는 동안 새로고침에도 유지된다
  3. 전달메시지를 보낼 때마다 x-chat-key 헤더로 백엔드에 전달 — URL·쿼리로는 절대 보내지 않는다
  4. 사용백엔드는 그 요청 안에서만 키를 쓰고 OpenAI SDK에 넘긴다 — 콘솔·파일 로그에 남기지 않는다
  5. 삭제패널 헤더의 “키 삭제”로 즉시 제거 + 대화 초기화 — 401 응답도 재입력 화면으로 되돌린다(대화는 유지)

보안 원칙과 한계

  • 영속 저장 금지 — .env, localStorage, 백엔드 저장소 어디에도 쓰지 않는다. 다른 탭·다른 창에서도 이 키를 볼 수 없다.
  • 로그 금지 — 백엔드 미들웨어·오류 응답 어디에도 키 원문을 출력하지 않는다. 오류 메시지는 “키가 거부되었습니다”까지만.
  • 공용 PC 안내 — 시작 화면에 “키는 이 탭에만 저장됩니다. 공용 PC에서는 사용 후 키 삭제를 권장해요” 문구를 넣는다.
  • 알려진 한계 명시 — sessionStorage는 같은 탭의 스크립트(XSS)에는 노출될 수 있다. localStorage보다 좁은 선택이지 완전한 보호는 아니며, 이 점을 시작 화면 문구에 담는다.

07

대화 컨텍스트 설계

답변의 신뢰도는 프롬프트 설계에서 나온다. 매 전송마다 두 덩어리를 보낸다 — 대화 기록(최근 12턴)과 대시보드 스냅숏(방금 재계산).

스냅숏 구조 — buildChatSnapshot()

// data/chatContext.js — 값은 예시, 실제로는 전송 시점에 재계산 { "asOf": "2026-10-01", // mockData 기준일 (dashboard.js의 DATA_AS_OF) "today": "2026-10-02", // 스냅숏 계산 시점 "kpi": { "contests": 4, "myContests": 2, "wishlist": 3, "savedIdeas": 1 }, "deadlines": [ { "title": "통합 라디오 애플리케이션 아이디어 공모", "organizer": "한국방송통신전파진흥원", "deadline": "2026-10-09", "kinds": ["접수 중", "응모"], "left": 8, "label": "D-8", "tone": "soon" } ], "fields": [{ "name": "기타", "count": 2 }, { "name": "환경", "count": 1 }, { "name": "생활", "count": 1 }], "sparks": { "combos": 384, "todayMission": "오늘의 미션 문구", "fields": ["…"], "whos": ["…"], "forms": ["…"] }, "notif": { "subscribers": 1, "email": { "total": 4, "real": 4 }, "sms": { "total": 2, "real": 0 } } } // notif는 백엔드 실패 시 null
  • D-x는 이미 계산된 값 — AI가 마감일에서 남은 일 수를 다시 계산하지 않는다. 스냅숏의 left·label·tone(urgent/soon/calm/closed)을 그대로 쓰게 강제한다.
  • 전송마다 재계산 — 날짜가 바뀌면 D-x도 바뀌어야 하므로 스냅숏은 캐시하지 않는다.
  • 릴 원본 포함 — 브레인스토밍 요청에 실제 조합(분야 6·대상 8·형태 8)으로 답하도록 슬롯머신 릴 배열을 그대로 넣는다.

시스템 프롬프트 (요약)

당신은 공내비 대시보드 도우미 "나비"입니다. 규칙: - 모든 사실은 [대시보드 스냅숏]에만 근거한다. 없는 정보는 "스냅숏에 없어요"라고 답한다. - 날짜 계산을 하지 않는다. 남은 일 수는 스냅숏의 left·label을 그대로 쓴다. - 데이터 기준일(asOf)을 함께 안내한다 — "기준일 2026-10-01 데이터예요". - 추천 후보는 스냅숏의 공모전만. 앱 밖은 "국내 공모전 전체 검색"을 안내한다. - 마감 임박(tone이 urgent) 공모전을 먼저 안내한다. - 답변은 한국어로 2~5문장. 정리가 도움되면 짧은 목록을 쓴다.

토큰 절약 장치

  • 스냅숏 축약 — 공모전은 제목·주최·마감일·상태만. 포스터·링크·설명은 제외한다.
  • 대화 기록 상한 — 최근 12턴(사용자+봇 각 6)만 전송하고, 오래된 턴은 잘라낸다.
  • 백엔드 무상태 — 서버는 대화 기록을 저장하지 않는다. 기록의 유일한 보관처는 브라우저 메모리다.
결과 화면과 같은 고지 원칙. 패널 하단에 “답변은 AI의 참고 의견이며, 스냅숏 기준일 이후의 변동은 반영되지 않아요”를 상시 표시한다. 2026-10-01에 결과 화면에 넣은 고지 문구와 같은 체계다.

한 단계가 끝나면 바로 확인하는 순서다. 단계 1–2(백엔드+스냅숏)와 단계 3(패널 골격)은 서로 독립이라 병렬로 진행할 수 있고, 단계 4부터 실키가 필요하다.

09

리스크와 대응

챗봇의 값은 모델 가용성과 키 관리에 달려 있다. 예상되는 문제와 대응을 미리 정한다.

리스크대응
게이트웨이 CORS·직접 호출 불가처음부터 백엔드 프록시로 설계 — 브라우저 직접 호출 경로를 아예 만들지 않는다
키 유출영속 저장 금지 + 헤더 전송 + 로그 금지. 더 강한 운영이 필요해지면 “서버 .env의 단일 운영 키로 전환” 확장 경로를 남긴다(시작 화면 UX는 그대로 유지)
gpt-5-luna 응답 지연·장애60초 타임아웃 + 타이핑 인디케이터 + 재시도 버튼. 챗봇이 죽어도 대시보드 본체는 영향 없다(별도 컴포넌트)
토큰 비용스냅숏 축약 + 대화 12턴 상한. 길어진 대화는 자동 절단하고 안내 문구로 알린다
모델이 사실을 지어냄시스템 프롬프트 규칙(스냅숏 밖은 모른다고 답하기) + 패널 하단 고지 문구
마감일이 지난 뒤 잘못된 D-x전송마다 스냅숏 재계산 + asOf·today를 함께 전달해 기준을 명시
키 분실키는 사용자가 보유한 것 — 재입력 화면이 곧 복구 절차다. 별도 복구 수단을 만들지 않는다
10

검증 체크리스트

완성 판정 기준. 01장의 “근거 있는 답변” 원칙이 실제로 지켜지는지로 판정한다.

  • 키 없이는 전송되지 않음 — 전송이 차단되고 시작 화면이 유지된다
  • 사실 답변이 스냅숏과 일치 — D-x·건수·목록을 대시보드 화면 값과 대조한다 (예: “D-8 통합 라디오 애플리케이션 아이디어 공모”)
  • 오류 3종 동작 — 401 재입력 전환(대화 유지) / 502 재시도 버튼 / 백엔드 꺼짐 안내 문구
  • 탭을 닫으면 키·대화 소멸 — sessionStorage 동작 확인, 백엔드 로그에 키 원문이 남지 않음
  • 기술 검증 — tsc 통과, npm run dev로 백엔드+프론트 동시 구동 확인, 320px에서 가로 스크롤 없음
  • 기존 화면 회귀 없음 — 대시보드 외 화면은 수정 없음, 대시보드 자체는 도크가 떠는 것 외 레이아웃 변화 없음
이후 확장 (이번 범위 밖). SSE 스트리밍 답변(타이핑 효과), 대화에서 바로 “이 공모전 응모하기” 액션 연결, 결과 화면의 아이디어를 컨텍스트로 이어받기. 스냅숏 구조를 만들어 두었기 때문에 셋 모두 프롬프트·스냅숏 확장으로 처리된다.
